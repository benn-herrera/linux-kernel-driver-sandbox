# SPEC – api_gen

The consumer-facing contract of the API generator: what a definition may say, and what every compliant implementation produces from it. How this implementation does so is in ARCHITECTURE.md beside this file. Where the generator sits in the build is in the root ARCHITECTURE.md, "API generation".

## Purpose

A userspace API is stated once, in a definition file, and every artifact a consumer needs is generated from it: a C header that also carries, for the implementation's build only, a compile-time check that the library's constants agree with the driver's UAPI header; a header-only C++ wrapper; a LuaJIT module; and an implementation stub. The definition is the source of truth; the artifacts are build products and are never edited. The definition states meaning, not shape: each output is idiomatic for its own language, and no output copies another's form.

## The definition

One TOML file, `<stem>.adef.toml`. `<stem>` names every output.

Every key that is not a name begins with `_`, at every level: every other key is a member name (a constant, field or parameter), and no member name begins with `_`. `[_general]` describes no item, so every one of its keys is a `_`-prefixed property too. `[_driver_data]` describes no item either: it holds the property `_header` and the member map `[_driver_data.const_pins]`, whose keys are names.

- Item properties: `_docstring` (documents the item), `_return` (functions only), `_base_type` (enums and constant groups only), `_to_string` (enums, bit and plain constant groups only), and on an opaque ref `_class`, `_ctor`, `_dtor`.
- Entry attributes: on a constant `_value`, `_docstring`, and for an integer `_format`; on a struct field `_type`, `_docstring`; on a parameter `_type`, `_ref`, `_count`, `_optional`, `_docstring`.
- A naked value is sugar: a constant `name = 4` (or `name = ["a", "b"]`) is exactly `name = { _value = 4 }`, and a field or parameter `name = "u32"` is exactly `name = { _type = "u32" }`. An inline table and a nested `[a.b.c]` table are the same thing; both are accepted everywhere.
- `_ref` states how the callee reaches a parameter: `"in"` is read by the callee, `"out"` is written by it, `"inout"` is both; absent means by value. A `memory` parameter requires `_ref`.
- `_count` is one of the unsigned integer types `"u8"`, `"u16"`, `"u32"`, `"u64"`, required on a `memory` parameter and allowed nowhere else: the type of the buffer's byte count.
- `_optional = true` marks an `in`, `out` or `inout` struct or scalar parameter, or a `memory` parameter with `_ref = "in"`, as one whose null the caller may pass instead of a value; refused everywhere else, naming the parameter: on a parameter with no `_ref` (a by-value parameter has no null to pass) and on a `memory` parameter with `_ref = "out"` or `"inout"`. A constructor's cached `out` parameter (see the C++ wrapper and the Lua module below) ignores it, since the binding always supplies that parameter itself.
- `_format` is `"hex"` or `"dec"` (the default): how the number is spelled where a literal is emitted.
- `_to_string = "<name>"` asks for a function converting a value of the group to text, named `<name>` as each output's section below states; absent, no conversion is generated for the group. `<name>` is a name like any other: the identifier and keyword rules below apply to it. An enum converts a value to its entry's unprefixed name (`"ERR_TIMEDOUT"`), the later entry where two share a value, and a value no entry has to `UNKNOWN_<ENUM>` (`UNKNOWN_RESULT`). A plain group does the same, with `UNKNOWN` for a value no entry has. A bit group decomposes the value: each entry with exactly one bit set, in document order, whose bit is present contributes its unprefixed name and removes its bit; the names are joined with `|`, and any bits left over follow as one final term, `0x` and their lower-case hex without padding; zero converts to `NONE`. A composed entry with more than one bit is never matched: with entries `a` bit 0, `b` bit 1 and `ab = ["a", "b"]`, 3 converts to `A|B`, 1 to `A`, 0 to `NONE` and 9 to `A|0x8`.

The file holds these tables, each optional unless stated; any other top-level table is an error:

- `[_general]` (required): `_namespace` (an identifier; the prefix for everything generated), `_version` (four integers 0..255, encoded most-significant first into one 32-bit value), `_library` (the shared object file name the script binding loads; a plain file name, no quotes, backslashes or control characters). There is no name field: the file stem names every output.
- `[[untyped_bit_const]]`: an array of groups of constants that are bit flags. Each group has an optional `_docstring`, an optional `_base_type`, an optional `_to_string`, and at least one entry. An integer value is a bit index whose flag is a positive value of the group's base type: 0..30 under `i32`, 0..31 under `u32`. A list sums its terms into the entry's value: each term is an earlier entry of this group or of an earlier group of the same base type, or a literal integer fitting the base type, written as a string in decimal or in hex with a lower-case `0x` prefix, either with an optional leading `-` and nothing else (`"4"`, `"-4"`, `"0x1f"`); any other term that is not an entry name is refused; the loader refuses a term naming an entry of another base type, naming both entries and both base types, and a sum whose terms share a bit, naming the two.
- `[[untyped_const]]`: an array of groups of plain integer constants, with the same group properties. A value is an integer fitting the group's base type (`i32`: -2^31..2^31-1; `u32`: 0..2^32-1), or a list summing the same kind of terms `untyped_bit_const` composes — an earlier entry of this group or of an earlier group of the same base type, or a literal integer fitting the base type — with that range applied to the sum; a term naming an entry of another base type is refused the same way. A floating-point value, or a `_base_type` of `f32` or `f64`, is refused as not implemented.
- `[[string_const]]`: an array of groups of string constants, each with an optional `_docstring` (no `_base_type`: a string has no fixed-width representation; no `_to_string`) and at least one entry. Values are strings containing no `"`, `\` or control character (U+0000..U+001F, U+007F).
- `[typed_const.<enum>]`: an enumeration, with an optional `_docstring`, `_base_type` and `_to_string`. Values are integers fitting the enum's base type.
- `[opaque_ref.<name>]`: a handle type whose representation is the implementation's secret. It has no members, only properties: `_docstring`; and for bindings with object semantics, `_ctor`, the function that produces the handle (it has exactly one parameter of this type with `_ref = "out"`), `_dtor`, the function that releases it (its only parameter is this type by value; requires `_ctor`), and `_class`, the object's name in those bindings, written idiom-free (lowercase identifier; default the ref's name). Each binding applies its own casing.
- `[struct.<name>]`: an optional `_docstring`, then fields in document order.
- `[function.<name>]`: `_return` (a `typed_const` enum name whose entries include the value 0, required), an optional `_docstring`, then parameters in document order. A `memory` parameter `p` becomes, in the C header and every output that mirrors it, an adjacent pair: the pointer `p`, then its byte count `p_count` of the `_count` type. The definition does not write the count; a numeric parameter written beside a buffer is just another parameter.
- `[_driver_data]`: `_header`, the driver's UAPI header path relative to the exercises directory (no quotes, backslashes or control characters), and `[_driver_data.const_pins]`, mapping an `untyped_bit_const` key to the driver macro it must equal.

`_base_type` is `"i32"` (the default) or `"u32"`, and chooses the fixed-width type of an enum or a group's constants: the C header types a group's constants by it, the C++ wrapper takes that type from the header, and the wrapper's enum classes and the Lua FFI declarations name it.

Rules a definition must satisfy:

- Types are the integer types `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, the floating-point types `f32`, `f64`, `memory`, or a name from `typed_const`, `opaque_ref` or `struct`. The builtins other than `memory` are variable types only: `_base_type` and `_count` take the values stated for them. Those three categories share one namespace; a name in two of them is an error, as is shadowing a builtin.
- A key beginning with `_` that is not recognised where it appears is an error naming the key and where; so is a key not beginning with `_` inside an entry's table or an opaque ref. `[untyped_const]`, `[untyped_bit_const]` and `[string_const]` written as single tables are an error: each is an array of tables, `[[...]]`. A group has at least one entry.
- A `memory` parameter's `p_count` is not the name of another parameter of the same function.
- Every name is a C identifier that is neither a C, C++ nor Lua keyword. No parameter is named like a name a binding's generated code itself uses where that parameter is in scope; each binding's section below says so.
- A composed constant names only entries defined before it, in its own group or an earlier one of the same `_base_type`. A pin names an existing `untyped_bit_const` entry. Constant names are unique across every constant group, the string constants, every enum, and the version constant; the C identifiers of enums, opaque refs and their tags, structs and functions are unique together.
- Docstrings contain neither `*/` nor `]]`.
- Order is meaning: parameters, fields and constant groups appear in every output in the order written.
- A ctor has no `memory` parameter with `_ref = "out"` and no parameter with `_ref = "inout"`: the bindings cache every other `out` of the ctor on the object, a buffer has no owner there, and a constructor has nothing to return an updated value through.

## Naming

With namespace `ns`, upper-cased `NS`:

| definition | generated |
|---|---|
| bit, plain, string constant or enum entry `key` | `NS_KEY` in C; `KEY` in a module-scoped binding |
| `_general._version` | `NS_API_VERSION` |
| enum `e` | `enum ns_e`, typedef `ns_e` |
| opaque ref `h` | `struct ns_h_opaque`, typedef `ns_h` (a pointer) |
| struct `s` | `struct ns_s`, typedef `ns_s` |
| function `f` | `ns_f` |
| `_to_string` `f` on enum `e` | `ns::f`, overloaded on `ns::E`, in C++; `M.e_f` in Lua |
| `_to_string` `f` on a bit or plain group | `ns::f` in C++; `M.f` in Lua |
| `memory` parameter `p` | `p`, then its byte count `p_count` |
| in C++: enum `e`, entry `k`, struct `s`, class `c` | `ns::E`, `E::K`, `ns::S`, `ns::C` (UpperCamel) |
| `_base_type` `i32`, `u32` | `int32_t`, `uint32_t` as a type; `INT32_C`, `UINT32_C` on a literal in the C header |
| visibility macros | `NS_C_API`, `NS_API`, with `NS_IMPL` as the implementation's define |

## Outputs

Every output starts with a banner naming its source and saying it is generated. Under the output directory:

### `include/<exercise>/<stem>.h` — the C header

- For a consumer, includes only `<stdint.h>`. Its preprocessor content is: `#pragma once`, that include, the two blocks defining `NS_C_API` (`extern "C"` under C++) and `NS_API` (`NS_C_API` plus default visibility when `NS_IMPL` is defined), one `#define` per bit or plain constant and for the version, and the implementation-only blocks below. No macro is used in any declaration except `NS_API` before each function.
- One block at the end of the file under `#if defined(NS_IMPL)`, and so only in the implementation's build: an include of `<assert.h>` and of the driver header named in `_driver_data._header`, then one file-scope `static_assert(NS_KEY == DRIVER_MACRO, "...")` per pin. The library failing to compile is the ABI check; a consumer never sees the driver header. Absent `[_driver_data]`, the block is not emitted.
- The version and every bit and plain constant are object-like macros, `#define NS_KEY <value>`, each typed by its `<stdint.h>` constant macro. The version is `UINT32_C(0x...)`, its four bytes as eight hex digits. In a group, the base type's macro (`INT32_C` for `i32`, `UINT32_C` for `u32`) wraps a literal value, spelled per `_format`, and a single bit's one: `INT32_C(16)`, `UINT32_C(0xbeef)`, `(INT32_C(1) << n)`. A negative value keeps its sign outside the macro, which wraps its magnitude, `(-INT32_C(0x5))`; the base type's minimum, whose magnitude the type cannot hold, is `(-INT32_C(0x7fffffff) - 1)`, spelled per `_format` the same way. A composed entry's sum is symbolic and parenthesised, `(NS_A | NS_B)` in a bit group and `(NS_A + NS_B)` in a plain group, a literal term rendered as a literal value is, in the base it was written in, `(NS_A | INT32_C(4))`, `(NS_A + (-INT32_C(0x3)))`. Each group is one run of macros under its docstring comment. Each typed enum is an enum with explicit values and a typedef, a non-negative value spelled per `_format` and a negative one as a negative group value is. Each string constant group is a run of `static const char NS_KEY[] = "...";`.
- Each opaque ref is an incomplete struct and a pointer typedef. Each struct has its fields in order with a typedef.
- Functions are declared in document order. Type mapping: an integer type `iN` → `intN_t` and `uN` → `uintN_t`, `f32` → `float`, `f64` → `double`, an enum or struct by its typedef, an opaque ref by value as its typedef; a non-memory type `T` with `_ref = "in"` → `const T*`, with `"out"` or `"inout"` → `T*`; `memory` → `const void*` when `"in"`, `void*` when `"out"` or `"inout"`, followed by `p_count` of its `_count` type.
- Docstrings become `/* */` comments: above a constant group, enum, struct, opaque ref or function, trailing a constant, enum entry or struct field; a parameter's docstring joins its function's comment as `name: text`.
- The header carries no `_to_string` conversion.
- A constant of any kind, an enum entry included, whose C name is one of the header's own macros, `NS_C_API`, `NS_API`, `NS_IMPL` or `NS_API_VERSION`, is refused, naming the constant and the macro.
- A typed enum's entries are C enumerators whatever the base type, and a C17 enumerator is an `int`: an entry whose value exceeds the `i32` maximum, as `u32` otherwise allows, is refused, naming the entry.
- The header is not a binding input. The Lua module carries its own FFI declarations, rendered from the same definition, so nothing parses the header at run time and the implementation-only blocks may hold whatever the check needs.

### `include/<exercise>/<stem>.hpp` — the header-only C++ wrapper

A C++20 header beside the C header, including it and nothing but the standard library, inside `namespace <ns>`. Constants are `inline constexpr` under their unprefixed names, each constant group — bit, plain or string — one run under its `_docstring` as a `//` line: the version and every bit and plain constant `auto`, initialised from its header macro and so typed as the header types it, a string constant `const char*`; each enum is an `enum class` over the C values with its base type as the underlying type and UpperCamel entries; each `_to_string` conversion is an `inline` function under the namespace — an enum's `const char* f(E value)`, a `switch` over the enum class, so enums may share `f` as overloads; a bit or plain group's `std::string f(T value)`, `T` the group's base type, following the group's constants; each struct is an alias of the C typedef. Each opaque ref with a `_ctor` is a class named from `_class` in UpperCamel, move-only (move assignment releases the current handle first): `create(...)` takes the `_ctor`'s parameters other than its non-memory `out`s and returns the class by value, with the call's result written through an optional out-pointer; on failure the object is falsy (null handle, value-initialised members), so `if (!dev)` is the check and no optional is involved; every other `_ctor` `out` is a private member read through a const accessor named after its parameter, `dev.info()`; the destructor and `release()` call the `_dtor`; one method per function, other than the `_ctor` and `_dtor`, whose first parameter is the opaque by value, returning the enum and taking a `memory` parameter as the C header does, pointer then count. A non-memory `in` is `const T&` (a struct by its alias), an `out` or `inout` `T&`, each passed to C by address; an `_optional` struct or scalar `in`/`out`/`inout` method parameter is `const T*` or `T*` instead, forwarded as-is, defaulted to `nullptr`; defaults are trailing, so an `_optional` parameter followed by a non-optional one keeps the pointer type but has no default. A constructor's cached `out` parameters ignore `_optional`. An opaque by value is the C handle type; an enum reached through `_ref` is the C typedef. Results are `[[nodiscard]]`. Casts are functional-style, C names unqualified, fixed-width integers spelled as the C header spells them. No exceptions; no allocation but the `std::string` a group's conversion returns. A conversion name the namespace already defines is refused, as is one two conversions share unless both are enums'. A parameter named like a name the class's own code uses beside parameters (`create()`'s `result` and `status`, the private constructor's `handle`, the `handle_` member, and every name it renders from the definition there: the C functions and typedefs, the fixed-width integer types, and the namespace's enum classes, struct aliases and classes) is refused, naming the parameter; so is a method named like one of the rendered names, and a method or cached `out` named like another member or like the class's own name, `create`, `handle`, `handle_`, or `release` where a `_dtor` generates it.

### `stub/<stem>.cpp` — the implementation stub

A C++ translation unit to copy into `lib/` once when starting an implementation, never staged and never touched by the generator afterwards: the implementation-macro define around the header include, so the ABI pins compile, the standard headers `<cerrno>`, `<cstdint>` and `<cstring>`, and one definition per function in document order whose body voids every parameter with a `(void)` line, then a `// replace: not implemented` comment, then `return {};`, which C++ value-initialises the return enum to its zero entry. The signatures match the header byte for byte.

### `binding/<stem>.lua` — the LuaJIT module

A module returned from `require`, needing no file at run time:

- Its `ffi.cdef` text holds only what calls need: `typedef int32_t ns_e;` for each enum (`uint32_t` under `_base_type = "u32"`), the opaque and struct declarations, and the functions without `NS_API`. No constants are declared to the FFI.
- Every constant is a Lua literal, `M.KEY`, with the same value the header gives it: the module is the namespace, so the `NS_` prefix is not repeated. A composed entry's sum is computed; strings are string literals; the version is one 32-bit value. A constant group's `_docstring` is a `--` comment line above its literals.
- A bit flag whose value exceeds 2^31-1, as a `u32` group's bit 31 does, is refused: LuaJIT's `bit` operations are signed 32-bit, so the flag would not equal its own masked result.
- Each `_to_string` conversion is a module function taking the value, an enum's `M.<enum>_<f>(value)`, since Lua has no overloading, and a bit or plain group's `M.<f>(value)`. Every conversion returns the string `"nil"` for `nil`, as `tostring(nil)` does. A conversion's name equal to a constant's, a class's, `raw` or another conversion's is refused.
- A parameter becomes a Lua local of its class function, so one named like a name the module uses where it would be in scope (the module's locals `M`, `ffi`, `bit`, `lib`; the globals it calls, such as `assert`, `type` and `tonumber`; a class function's own locals, such as `self` and `result`) is refused, naming the parameter.
- `M.raw.<f>` is the FFI function for each function.
- For each opaque ref with a `_ctor`, a class `M.<Class>`, the `_class` attribute in UpperCamel with no namespace prefix:
  - `new(...)` takes the `_ctor`'s parameters other than its non-memory `out`s, in order; returns `nil, result` on any result other than the enum's zero-valued entry, else an object whose `_handle` is the opaque value with the `_dtor` as its GC finalizer, and which caches every other `out` of the `_ctor` under that parameter's name: a struct as a plain table copy of its fields (`i64` and `u64` fields as cdata, every other builtin and enum field as a number, nested structs copied the same way), an `i64` or `u64` scalar as cdata, any other builtin or enum scalar as a number. The module emits no display helpers; what a consumer prints is the consumer's.
  - One method per function, other than the `_ctor`, whose first parameter is the opaque by value, taking the other parameters except non-memory `out`s, in order. A non-memory `in` or `inout` value is passed as a Lua value, a struct as a table or cdata and a scalar as a number, and copied into cdata the C call points at; for an `_optional` `in` or `inout` parameter this copy happens only when the caller's value is non-nil, and `nil` passes straight through so the FFI turns it into a null pointer. After a successful call the `out` and `inout` non-memory values are returned in order, a struct as the same plain table, an opaque as the raw handle unwrapped, followed by `nil`; a method with none returns `true, nil`; any other result returns `nil, result`.
  - The `_dtor`'s method releases explicitly: it disarms the finalizer if one is attached, calls the function with whatever `_handle` holds, clears `_handle`, and returns like any method. A second release therefore reaches the library as a null handle and returns whatever the library promises for that, so the function's own contract holds through the class. An object never released is released by the GC finalizer.
  - Every other method begins with an `assert` that `_handle` is set. Use after release is a caller bug and fails as an assertion; the `nil, result` return is reserved for what the library reports.
  - `new` and every method, the `_dtor`'s included, then asserts the type of each of its own arguments in order, one `assert` per argument, after the live-handle assert where there is one and before any FFI allocation or call: `type(x) == "number"` for every builtin other than `i64` and `u64`, a typed-enum value, and a `memory` `out` argument's count; `type(x) == "number" or ffi.istype("uint64_t", x) or ffi.istype("int64_t", x)` for `i64` and `u64` by value or `inout`, since a literal like `48ULL` may hold either C type; `type(x) == "string"` for a `memory` `in` or `inout` argument; `type(x) == "table" or ffi.istype("ns_s", x)` for a struct `s` by `in` or `inout`; `ffi.istype("ns_h", x)` for an opaque `h` passed by value — never a bare `type(x) == "cdata"`, which would accept any cdata regardless of its C type. The message is `"<Class>.<method>: <param> must be <expected>"`, e.g. `"Device.dma_to_device: psrc must be a string"`, `"Port.configure: cfg must be a table or xy_stats"`. An `_optional` parameter's condition gains `x == nil or` and its expected text gains " or nil".
  - An opaque ref without a `_ctor` gets no class; its functions are reachable through `M.raw`.
  - A `memory` parameter is a Lua string, the idiomatic byte container; the generated code never exposes a cdata buffer to the consumer. `_ref = "in"`: the argument is the string, passed straight to the call with its length as `p_count`; `_optional` admits `nil`, passed straight through with a `p_count` of 0. `_ref = "out"`: the argument, in the parameter's position, is `p_count`, a number; the method allocates a buffer of that size, passes it and `p_count` to the call, and returns the bytes written as a string in the out-values position, exactly as a scalar `out` is returned. `_ref = "inout"`: the argument is a string; the method copies it into a buffer of the same length, passes that and its length to the call, and returns the bytes written as a string the same way.
- Results, constants, enum values and every builtin other than `i64` and `u64` are plain Lua numbers. `i64` and `u64` values are cdata: they compare with numbers and print with a `ULL` suffix, and `tonumber` would silently truncate above 2^53.

## Invocation

Two modes. Generation: `python3 -m api_gen <definition> --generated <dir> --exercise <name> [--library <file>] [--outputs=<list>]`. `--outputs` names the outputs to produce as a comma-separated list of tokens: `h` (the C header), `hpp` (the C++ wrapper), `lua` (the Lua module), `stub_cpp` (the implementation stub); absent, all four. An unknown or repeated token is a usage error, exit status 2 with a message listing the valid tokens. No output implies another: the wrapper and the stub include the header, but selecting them neither adds `h` nor requires it. `--library` overrides `_general._library` and is held to the same rule, an empty one being a usage error; one of them must be present when `lua` is selected. Exit status 0 on success with one line on stderr naming what was written; 2 on any definition error, with nothing written and each objection on its own line as `api_gen: <definition>: <what is wrong>`. A definition that breaks the format's own rules draws its first objection; one that satisfies them draws every objection every selected output has, and none from an output not selected, all in the same run, each once, as `api_gen: <definition>: <outputs>: <what is wrong>`, where `<outputs>` names every selected output raising that same objection, comma-joined in the order `header`, `wrapper`, `lua`, `stub` (`header, wrapper, stub: struct.stats.int: 'int' is a C keyword`). A definition the format allows but the generator does not yet produce is refused the same way, the message saying `not implemented`. Every selected output is always written, and no other; staleness is the build's concern.

Dependencies: `python3 -m api_gen gendeps [--outputs=<list>] <definition>` prints make text to stdout for exactly one definition (one per exercise is the rule): `GENERATED :=` listing the selected outputs, `--outputs` as generation reads it, as `$(GEN)/...` paths with `$(BASE)` for the exercise directory, and one grouped-target rule (`$(GENERATED) &: definition`, GNU make 4.3 or later) making them by running the generation mode with `--generated $(GEN) --exercise $(BASE)` and the same selection as `--outputs`. The including makefile defines `GEN`, `BASE` and `API_GEN`. The definition is not read; only its name matters, and the output paths come from the same code the generation mode writes to, so a build file never spells them.

## Not generated

The kernel ioctl header. Its shape is a kernel UAPI header's, not a userspace API's, and it is hand-written; the pins are the bridge. The API's implementation is hand-written too: the stub is a starting point handed over once, and the generator never touches `lib/`.
